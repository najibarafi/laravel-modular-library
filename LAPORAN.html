BAB I — PENDAHULUAN

1.1 Latar Belakang

Aplikasi perpustakaan melibatkan beberapa area bisnis yang berbeda: pengelolaan data buku, pengelolaan anggota, serta proses peminjaman dan pengembalian. Pada praktik sebelumnya, seluruh logika sering ditempatkan dalam satu struktur yang bercampur. Ketika jumlah fitur bertambah, pendekatan tersebut menyulitkan pemeliharaan karena batas tanggung jawab antar bagian menjadi kabur.

Praktikum Pertemuan 6 memperkenalkan modular monolith dan Domain-Driven Design (DDD). Aplikasi tetap berjalan sebagai satu kesatuan (satu proses Laravel dan satu database), tetapi kode dipisahkan menjadi beberapa bounded context dengan tanggung jawab yang jelas. Setiap context memiliki model, migration, route, dan service sendiri. Komunikasi lintas context dibatasi melalui contract sehingga ketergantungan antar modul tetap terkendali.

Sistem yang dibangun pada laporan ini adalah Sistem Perpustakaan dengan tiga bounded context: Catalog (buku, penulis, kategori, penerbit), Membership (anggota, role, keanggotaan), dan Circulation (peminjaman, pengembalian, denda). Aplikasi juga menerapkan relasi database lanjutan, optimasi query, transaksi atomik, soft delete, domain event, dan Value Object.

1.2 Rumusan Masalah

  1. Bagaimana merancang struktur modular monolith dengan pemisahan bounded context yang jelas?
  2. Bagaimana mengimplementasikan relasi Eloquent lanjutan (Many-to-Many dengan pivot, self-referencing, dan HasMany) pada sistem perpustakaan?
  3. Bagaimana menjaga konsistensi data saat peminjaman buku menggunakan transaksi database?
  4. Bagaimana mengoptimalkan query untuk menghindari masalah N+1?
  5. Bagaimana menerapkan soft delete, restore, domain event, dan Value Object dalam studi kasus nyata?

1.3 Tujuan

  1. Membangun aplikasi Laravel dengan struktur modular per bounded context.
  2. Mengimplementasikan relasi database lanjutan beserta bukti pada antarmuka.
  3. Menerapkan transaksi atomik dan rollback pada proses peminjaman.
  4. Mengukur dan mengurangi jumlah query menggunakan eager loading dan query scope.
  5. Menerapkan soft delete/restore, domain event, Value Object ISBN, dan Value Object Denda.
  6. Menyediakan pengujian otomatis untuk memverifikasi seluruh aturan bisnis utama.

1.4 Manfaat

  • Bagi mahasiswa: memahami penerapan DDD dan modular monolith pada proyek Laravel nyata.
  • Bagi pengguna: memperoleh aplikasi perpustakaan yang mencatat peminjaman, stok, denda, dan riwayat secara konsisten.
  • Bagi pengembangan selanjutnya: struktur modul memudahkan penambahan fitur tanpa mengubah seluruh basis kode.

1.5 Batasan

  • Autentikasi menggunakan Laravel Breeze yang sudah tersedia; fokus praktikum pada tiga bounded context perpustakaan.
  • Database default menggunakan SQLite; skema dirancang agar tetap kompatibel dengan MySQL/PostgreSQL.
  • Pembayaran denda hanya menandai status lunas (belum terintegrasi payment gateway).
  • Notifikasi domain event ditulis ke file log, belum dikirim melalui email/queue.

BAB II — LANDASAN TEORI

2.1 Modular Monolith

Modular monolith adalah aplikasi yang di-deploy sebagai satu unit, tetapi kode internalnya dibagi menjadi modul-modul dengan batas tanggung jawab yang tegas. Keuntungannya: operasional sederhana seperti monolith, namun keteraturan kode mendekati arsitektur mikroservis.

Pada Laravel, modularitas diterapkan melalui namespace Modules\*, service provider per modul, serta pemisahan migration, route, dan view.

2.2 Domain-Driven Design dan Bounded Context

DDD menekankan pemodelan perangkat lunak berdasarkan bahasa dan aturan domain. Bounded context adalah batas di mana sebuah model dan istilah memiliki makna yang konsisten. Pada sistem ini:

  • Catalog berbicara tentang buku, stok, penulis, penerbit, dan kategori.
  • Membership berbicara tentang anggota, role, dan masa keanggotaan.
  • Circulation berbicara tentang peminjaman, pengembalian, denda, dan status peminjaman.

Karena Book adalah milik Catalog dan Member adalah milik Membership, context Circulation tidak mengakses model tersebut secara langsung. Circulation memakai BookServiceInterface dan MemberServiceInterface yang didefinisikan di Shared Kernel.

2.3 Relasi Eloquent

  • One-to-Many / HasMany: satu peminjaman memiliki banyak item (Loan::items()).
  • Many-to-Many: buku memiliki banyak kategori dan kategori memiliki banyak buku, dengan pivot book_category yang menyimpan added_at.
  • Self-referencing: kategori dapat memiliki induk dan anak (Category::parent() dan Category::children()).

2.4 N+1 Query dan Eager Loading

N+1 terjadi saat relasi diakses di dalam loop sehingga menambah satu query per baris. Eager loading (with()) memuat relasi dalam satu query tambahan sehingga jumlah query tidak tumbuh linear terhadap jumlah data.

2.5 Transaksi Database

Transaksi memastikan sekumpulan operasi diperlakukan sebagai satu kesatuan (ACID). Jika satu operasi gagal, seluruh perubahan dibatalkan. Laravel menyediakan DB::transaction() dan lockForUpdate() untuk mengunci baris selama transaksi.

2.6 Soft Delete

Soft delete tidak menghapus baris secara fisik, melainkan mengisi kolom deleted_at. Eloquent menyediakan trait SoftDeletes, method withTrashed(), onlyTrashed(), dan restore().

2.7 Domain Event

Domain event adalah objek yang menandai terjadinya peristiwa bisnis, misalnya BookBorrowed. Event dipisahkan dari aksi utamanya; listener menangani efek samping seperti pencatatan log.

2.8 Value Object

Value Object adalah objek immutable yang divalidasi saat dibuat dan tidak memiliki identitas sendiri. Pada sistem ini terdapat ISBN (validasi checksum) dan Denda (perhitungan otomatis).

4.7 Value Object ISBN

ISBN menormalisasi input (menghapus spasi/tanda hubung), memvalidasi checksum ISBN-10/ISBN-13, dan memastikan ISBN-13 berawalan 978/979.

final class ISBN
{
    public function __construct(string $value)
    {
        $normalized = strtoupper(preg_replace('/[\s\-]/', '', trim($value)) ?? '');

        if (! preg_match('/^(?:\d{9}[\dX]|\d{13})$/', $normalized)) {
            throw new InvalidArgumentException("Format ISBN tidak valid: '{$value}'.");
        }

        // validasi checksum ISBN-10 / ISBN-13 ...
    }
}

Contoh valid: 978-0-306-40615-7 → 9780306406157; 0-8044-2957-X → 080442957X.

4.8 Value Object Denda

Denda dihitung otomatis dengan tarif Rp 1.000 per hari dan pembulatan ke atas untuk keterlambatan sebagian hari.

public static function between(
    DateTimeInterface $dueAt,
    DateTimeInterface $returnedAt,
    float $ratePerDay = self::DEFAULT_RATE_PER_DAY,
): self {
    $secondsLate = $returnedAt->getTimestamp() - $dueAt->getTimestamp();

    if ($secondsLate <= 0) {
        return self::fromDaysLate(0, $ratePerDay);
    }

    $daysLate = (int) ceil($secondsLate / 86400);

    return self::fromDaysLate($daysLate, $ratePerDay);
}

Contoh: terlambat 3 hari → 3 × Rp 1.000 = Rp 3.000.

4.9 Transaksi Atomik dan Rollback

LoanService@borrow membungkus seluruh operasi dalam DB::transaction. Stok dikurangi dengan lockForUpdate() untuk mencegah race condition.

return DB::transaction(function () use ($memberId, $items, $notes, $changedBy) {
    $member = $this->memberService->getMemberForLoan($memberId);

    if (! $this->memberService->isEligibleToBorrow($memberId)) {
        throw new MemberNotEligibleException(/* ... */);
    }

    $loan = Loan::create([/* ... */]);

    foreach ($items as $item) {
        $book = $this->bookService->getBookForLoan($bookId);

        if (! $this->bookService->isStockAvailable($bookId, $quantity)) {
            throw new InsufficientStockException($book['title'], $book['stock'], $quantity);
        }

        $this->bookService->reduceStock($bookId, $quantity);
        LoanItem::create([/* snapshot */]);
    }

    $this->memberService->markAsBorrowing($memberId);
    LoanStatusHistory::create([/* ... */]);
    event(new BookBorrowed($loan));
});

Feature test memverifikasi bahwa ketika stok tidak cukup: loans, loan_items, stok, dan status anggota tidak berubah.

4.10 Domain Event dan Listener

Event BookBorrowed dan BookReturned ditangani listener yang menulis ke storage/logs/library-events.log.

class BookBorrowed
{
    public function __construct(public Loan $loan) {}
}

class LogBookBorrowed
{
    public function handle(BookBorrowed $event): void
    {
        Log::channel('library')->info('BookBorrowed', [
            'loan' => $event->loan->loan_number,
            'member' => $event->loan->member_name,
            'items' => $event->loan->items->count(),
            'borrowed_at' => $event->loan->borrowed_at->toDateTimeString(),
            'due_at' => $event->loan->due_at->toDateTimeString(),
        ]);
    }
}

BAB V — PENUTUP

5.1 Kesimpulan

  1. Sistem perpustakaan berhasil dibangun sebagai modular monolith dengan tiga bounded context (Catalog, Membership, Circulation) dan Shared Kernel berisi contract.
  2. Relasi lanjutan berhasil diterapkan: Many-to-Many book_category dengan added_at, self-referencing kategori, HasMany Loan → LoanItem, serta Many-to-Many member_role.
  3. Transaksi database menjamin konsistensi peminjaman: stok, record peminjaman, detail item, dan status anggota berubah bersama; kegagalan stok menyebabkan rollback total.
  4. Eager loading menurunkan jumlah query dari 12 menjadi 2 (peminjaman) dan 81 menjadi 3 (buku) pada data demo.
  5. Soft delete/restore, domain event, dan Value Object ISBN/Denda berfungsi dan terverifikasi melalui 57 test otomatis (181 assertion).

5.2 Saran

  1. Tambahkan antrean (queue) untuk notifikasi domain event agar tidak membebani request.
  2. Pisahkan database per context bila skala aplikasi tumbuh (langkah menuju microservices).
  3. Tambahkan kebijakan (policy) yang lebih granular daripada middleware role.
  4. Integrasikan payment gateway untuk pembayaran denda.
  5. Tambahkan observability (metrics/log terstruktur) untuk memantau performa query di produksi.
